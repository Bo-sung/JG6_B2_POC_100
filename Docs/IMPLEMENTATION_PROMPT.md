# 개발 에이전트 실행 프롬프트 — 100 LIVES VS 1 BOSS

> 아래 텍스트를 Unity 프로젝트를 다루는 Codex/개발 에이전트 세션에 전달한다. `README.md`, `GAME_DESIGN.md`, `MDA_ANALYSIS.md`, `TECH_SPEC.md`를 동일 작업 디렉터리의 `Docs/` 등에 복사한 뒤 시작한다.

---

당신은 **기존 Unity 7 프로젝트/템플릿을 이용해 게임 잼 POC를 실제로 제작하는 구현 에이전트**다. 보고서 작성으로만 끝내지 말고, 현재 저장소를 조사하고 **실행 가능한 한 개의 보스전 씬**까지 구현·테스트하라.

## 1. 프로젝트와 불변 목표

게임 가칭: **100 LIVES VS 1 BOSS**

**게임 잼 주제:** Inconvenient Superpowers (불편한 초능력).

**한 줄 기획:** 플레이어는 100개의 목숨을 가지고 체력이 매우 많은 정통 보스를 상대한다. 각 목숨에서 서로 다른 결함 있는 초능력 하나를 받는다. 능력은 매우 강하지만 사용자를 죽이거나 조작에 치명적 영향을 준다. 죽으면 우상단에 하찮은 킬로그가 남고 다음 능력을 가진 용사가 즉시 등장한다.

아래 문서를 **게임의 기준 사양**으로 읽어라.

1. `Docs/README.md`
2. `Docs/GAME_DESIGN.md`
3. `Docs/MDA_ANALYSIS.md`
4. `Docs/TECH_SPEC.md`

문서와 현재 템플릿이 충돌하면 게임 핵심 가치/불변 원칙을 훼손하지 않는 가장 작은 수정으로 조정하고 그 차이를 `Docs/POC_STATUS.md`에 기록하라.

### 절대 지킬 규칙

- **2D 사이드뷰 플랫포머 액션**. WASD 이동/방향, 점프, 대시, 평타.
- **한 생명에 능력 하나만** 장착. 패시브라면 기존 WASD/점프/대시/평타 동작을 바꾸고 스킬 키를 사용하지 않는다. 액티브라면 K(또는 템플릿의 Skill 액션)로 발동.
- **20종 능력 전체 구현**이 최종 POC 목표다. 20종 각각 5회, 총 100장. 세트당 20종을 한 번씩 섞는 **5세트 셔플백**.
- 플레이어 기본 1HP. 사망 시 1목숨만 소모, **보스 HP·페이즈 유지**, 기존 능력/물리 상태/예약 이펙트는 정리하고 빠르게 부활.
- **우상단 배그형 킬로그** 최대 5줄. 자해·낙사·벽 충돌·보스 피격의 사인과 피해자를 정확하게 표시.
- 보스 한 명: HP 높고 일반적인 보스 클리셰인 **횡베기/내려찍기/돌진/지면 충격파/마력탄/운석/레이저 7패턴**. 2페이즈.
- 특수 능력은 단순 마나/쿨다운 페널티가 아니다. 강력한 효과가 **사용자에게도 위험을 만들어내고, 플레이어가 위치/거리/타이밍으로 우회**해야 한다.
- 보스의 모든 기본 패턴은 초능력 없이도 이동·점프·대시로 회피 가능해야 한다.
- 구현물의 미술은 과장되고 짜치는 B급 스타일. **조작감·충돌 판정·가독성은 정확하게**.
- Unity 버전·패키지를 임의 변경하지 마라. 저장소가 Unity 7 알파라면 현재 버전의 실제 API에 맞춰 검증하라. 기존 템플릿·에셋·컨트롤러가 있다면 이를 우선 재사용.
- 아우터즈/108 무구 고유 명칭 및 묘사는 내부 가칭이다. 원작 동일성 및 공개 사용 허가를 가정하지 말고 데이터로 분리하여 변경 가능하게 하라.

## 2. 최초 행동: 저장소 점검

요청을 받은 즉시 다음 작업을 수행하라.

1. `ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json`, 기존 씬과 Input Actions, Player/Boss/Combat 코드, 2D 물리 구현 상태 확인.
2. 기존 템플릿의 사용 가능한 기능, 수정 필요 기능, 새 기능을 분류. 추측으로 프레임워크를 추가하지 마라.
3. 미리 정의된 `Docs/` 설계를 기준으로 **최소 구현 경로**를 짧게 요약하고 즉시 작업을 시작하라.
4. 프로젝트 전용 브랜치 또는 안전한 변경 기록을 남겨라. 사용자 작업물을 임의 삭제/대규모 교체하지 마라.
5. 원작 이름에 의존하는 코드/애셋 네이밍을 만들지 말고 `A01`~`A20`의 안정적 내부 ID를 사용하라.

## 3. 구현 아키텍처

POC는 **단일 Player 오브젝트**, `AbilityDefinition`(ScriptableObject 데이터) + `AbilityRuntime`(상태 보유) + `AbilityController`(1개 장착)를 기본으로 한다. `PlayerActionController`가 기본 `Move/Jump/Dash/Attack` 요청을 만들고 Passive가 해당 Request를 변경한다. Active는 `Activate`로 발동한다. 공통 `EffectSystem`, `DamageResolver`, `LifeManager`, `BossController`, `KillFeedUI`로 역할을 분리하라.

### 반드시 지킬 코드 규칙

- 기본 플레이어 스크립트에 능력별 `switch(abilityId)` 20개를 만들지 마라.
- ScriptableObject에 런타임 상태(쿨다운·충전·횟수)를 저장하지 마라.
- 사용자 자해와 보스 피해를 별도 로직으로 만들지 마라. 공통 HitContext와 피격 파이프라인을 재사용하라.
- 효과 생성 시 `lifeId` 소유권 부여. 사망하면 해당 목숨의 참격·투사체·예약 효과·일시 상태를 제거하라.
- 물리 제어는 PlayerMotor2D 중심으로, 입력 수집과 FixedUpdate 처리 분리. 실제 템플릿의 이동 제어가 있다면 파괴하지 않고 얇게 확장.
- 보스 HP/페이즈와 일시 공격 상태 분리. 리스폰 안전 조치를 하면서 보스 체력을 실수로 초기화하지 마라.
- 사망·승리는 중복 처리하지 마라. 자폭으로 보스와 마지막 목숨이 함께 죽으면 **승리 우선**.

## 4. 개발 진행 단계 (중간 마일스톤은 최종 범위 축소가 아님)

### M1 — 플레이 가능한 뼈대

- 씬 한 개(`ArenaPOC`), 카메라, 단순 캐릭터/보스 프리미티브, 이동/점프/대시/평타.
- 플레이어 1HP, 보스 HP, 간단 보스 패턴 3개부터 동작.
- 100장 덱·사망/부활·우상단 킬로그·승패 판정.
- 보스 HP 유지, 플레이어 상태 초기화 우선 검증.

### M2 — 공통 능력 시스템 확인

대표 다섯 능력을 먼저 **완전히** 동작시킨다.

- `A01` 핏빛 거미: 평타 시 남는 참격, 본인도 피해.
- `A02` 티알파의 날개: 대시 증폭·제어 곤란·고속 벽 충돌사.
- `A05` 공명의 천둥북: 방어 타이밍에 강력한 반격과 사용자 위험.
- `A13` 초근력: 평타 강화·자기 반동.
- `A16` 인간 폭탄: 액티브 폭발·보스 피해 해결 후 본인 사망.

이 단계에서 Passive/Active 전환, `lifeId` 소유권, 히트박스/자해 공통 판정, 킬로그의 정확성, 보스/플레이어 동시 사망 테스트를 끝내라.

### M3 — 보스 패턴 완성

B01 횡베기, B02 내려찍기, B03 돌진, B04 지면 충격파, B05 마력탄 3연사, B06 운석 낙하, B07 레이저 훑기를 완성하고 페이즈 1(5종)/2(7종+검증된 일부 연계)를 적용하라. 예고/실제 피격 위치를 일치시키고, 모든 패턴을 기본 조작으로 회피할 수 있는지 테스트하라.

### M4 — 나머지 능력 구현

`GAME_DESIGN.md`의 `A01`~`A20` 표를 **누락 없이** 구현하라. 각 능력마다 (1) 입력 경로, (2) 초월적 효과, (3) 사용자의 위험, (4) 보스에게 실제 피해를 줄 수 있는 상황, (5) 사망 원인을 검증하라. `A08`은 **점프 패시브**이며 소지형 자동 발동이 아니다. 프리미티브/공통 Effect를 적극 재활용하고 새 능력 때문에 기본 Player 코드가 불필요하게 오염되지 않게 하라.

### M5 — 통합 및 게임 잼 품질

- 20종×5번=100장 정상 순환, 능력별 한 번씩 등장하는 세트 검증.
- 우상단 5줄 킬로그, 현 능력 설명·목숨·보스 HP, 결과 UI.
- 보스·능력의 타격감/황당한 사망 전달력 강화. 화려한 에셋 수집보다 반응성 우선.
- 죽은 뒤 0.5~1초 내 재조작, 연쇄사·자해 오분류·물리 상태 누수 수정.
- 초기 보스 HP 1,200, 평타 8, 능력 피해 30~100, 자폭 최대 150은 가안. 경험을 보고 조정.

## 5. MDA 관점의 구현 우선순위

1. **Sensation:** 초월적인 한 방과 자기 파괴가 명확히 느껴지는가?
2. **Challenge:** 보스 예고·후딜과 사용자의 결함을 계산하는 재미가 있는가?
3. **Discovery:** 첫 시도에서 실패한 능력을 나중에 더 안전하게 쓰는 방법을 발견하는가?
4. **Fantasy/Expression:** 하찮은 용사가 전설적 힘을 다루고, 같은 능력으로 다른 방법을 시도하는가?

`MDA_ANALYSIS.md`의 실험 가설과 실패 다이내믹(능력 무시, 자살 리롤, 불가피한 연쇄사, 보스 HP 노동)을 바탕으로 튜닝하라. **추가 콘텐츠보다 이 경험을 먼저 검증**한다.

## 6. 테스트와 진단 기능

반드시 다음을 검증하라.

- 20개 ID가 정확히 각 5장씩, 100장 덱에 존재.
- 모든 Passive가 별도 스킬 키 없이 기본 행동으로만 발동.
- 보스 공격/자해/낙사/벽 충돌 시 정확한 사인 킬로그 출력.
- 플레이어 죽음 한 번에 목숨 정확히 1 감소, `DeathEvent` 중복 없음.
- 사망 후 능력 효과/코루틴/상태 정리, 보스 HP/페이즈 보존.
- 100번째 사망 및 보스 승리·동시 죽음 우선순위.
- 7개 보스 패턴의 기본 조작 대응 가능성.
- 20종 개별 고정 지급 테스트 및 최소 한 번의 100목숨 전체 실행 테스트.

Editor/Development에서 능력 강제 지급·보스 HP 조절·생명 소모·킬로그 시뮬레이션 가능하도록 최소한의 개발 메뉴/버튼을 제공하라. 플레이 테스트 데이터는 최소 `lifeIndex, abilityId, survivalSeconds, bossDamage, deathCause, bossPatternAtDeath`를 로그로 남겨라.

## 7. 결과물과 보고 형식

작업 완료 시 다음을 제출하라.

1. 실행 가능한 Unity 프로젝트의 `ArenaPOC` 씬과 실제 코드·에셋 변경 사항.
2. `Docs/POC_STATUS.md`: 단계별 완료 여부, 20종별 동작 여부, 7패턴별 동작 여부, 현재 Play 가능 상태, 발견 버그, 근거/테스트 결과.
3. `Docs/POC_TEST_REPORT.md`: 컴파일/테스트 결과와 최소 1회 전투 플레이 결과 또는 실행 환경 제약을 정확히 기록.
4. 조작법, 씬 실행 방법, 변경 파일 목록, 남은 위험 요소 요약.
5. 컨텍스트 압축/세션 인계 시 **절대 규칙, 구현된 ID, 미구현 ID, 발견 버그, 다음 단계**가 담긴 짧은 인수인계 메모.

**금지:** 설계 문서/클래스 뼈대만 생성하고 POC를 구현했다고 주장하지 마라. 코드가 컴파일되는지 확인할 수 없다면 '미검증'으로 정확히 표시하라. 기존 저장소를 직접 실행할 권한이 없는 환경에서는 실행하지 못한 사유를 보고하고, 확인 가능한 범위의 코드/에셋 구조까지 완성하라.

**최종 성공 기준:** 보스 한 명과 결함 있는 20종 능력의 100목숨 루프를 **게임으로 실제 플레이**할 수 있고, 죽을 때마다 우상단에 하찮은 킬로그가 쌓이며, 보스 HP가 유지된 채 플레이어가 다른 능력으로 곧바로 다시 전투에 참여한다.
